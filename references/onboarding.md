# First run and profile updates

Check authorized persistent storage for an existing versioned profile. Do not assume that conversation history, model memory, an attachment or a local file will persist into another execution environment. If multiple profiles exist, ask which to use. Validate before offering to run.

Without a confirmed usable profile, gather the following conversationally, usually in two or three related groups. Show defaults as choices, not as inferred user preferences. No regulatory review begins until the required profile is confirmed. Checking potential source endpoints for relevance is onboarding, not a live monitoring run.

1. **Jurisdiction and domain:** Which country, region, jurisdictions or international frameworks? Which legal/regulatory areas? Permit multiple national, subnational, supranational or international scopes and combined supranational law/national implementation. Examples of domains: financial crime, payments, banking, sanctions, privacy, cybersecurity/resilience, AI, consumer protection, or a user-defined area. Ask broad coverage versus named laws, articles or obligations. Confirm ambiguous territory names and legal level; a nonempty string alone is not a verified jurisdiction.
2. **Sources:** Identify relevant official legislation databases, government publications, regulators and consultations. Offer a proposed source list with direct endpoints, jurisdiction and domain mapping; verify issuing authority, current remit, endpoint and topical relevance before marking a source `verified`. Ask about additional authorities/publications. Do not treat example mappings as an exhaustive or verified source register. Optional sources still get an explicit coverage result; `required` denotes priority, not permission to silently skip them.
3. **Schedule:** Manual, daily, weekly, monthly or custom? For recurring proposals collect local time, IANA zone, weekday(s) or month day, and short-month behavior. Custom recurrence requires the scheduler's actual dialect and validation. Present as a proposal; activation is a separate authorized action. See [scheduling](scheduling.md).
4. **Reporting:** Language, maximum words and changes, executive/standard/detailed, Markdown/PDF/both, neutral design or custom, naming, storage and any delivery destination. Offer 600 words, 3 changes, standard detail, Markdown+PDF and `default_light`. Include operational impact and legal review questions unless disabled. Defaults use English only as a portable starter; confirm the desired language. Verify output/storage/delivery capabilities before promising them.
5. **Optional operational context:** General monitoring or a particular industry/function? Organization type, activities, products, processes, risk/compliance functions. Keep this optional and nonconfidential. Entity type and activity scope matter more than a company name; no company name is required.
6. **Confirmation:** Summarize scope, sources and their verification status, recurrence proposal, time zone, report preferences, optional context and persistence/delivery capabilities. Offer confirm, change individual settings, create another profile, run first report, or activate scheduling separately. Set `confirmed: true` and jurisdiction confirmations only after actual user confirmation. Source verification timestamps require actual endpoint/relevance checks.

Use one file per unique profile ID. For updates, load, modify only requested fields, validate and summarize the change. Reconfirm material scope, source, delivery or schedule changes. Preserve unchanged settings. Never turn a profile edit into schedule activation.

If persistence is unavailable, return a downloadable or inline JSON profile and ask the user to supply it next time. Do not claim it is saved in memory. Cloud execution must receive the profile via cloud-accessible storage or the authorized task payload. Local paths and local font files do not transfer automatically.
